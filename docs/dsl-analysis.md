# Dify DSL 现状解析（生产版本）

> 来源：`（生产勿动）AI超级搜索（加课程说明）.yml`
> 解析方式：只读解析 YAML 结构，未修改原文件、未外传。密钥/数据集 ID 略去。
> 结论用途：作为 v6 改造的起点基线。

---

## 1. 一句话结论

**当前 DSL 只实现了 1 类数据的检索：线下课程期数。**
其余 7 类（线上课程、领袖营、高EQ导师、6Q商城、文章、视频、音频）没有任何检索节点，全部落到同一个 `other` 分支，返回「小Q暂不支持其他类型的智能检索哦」+「去全部看看」按钮。

所以 v6 不是「扩意图」这么轻——是**要新建 7 类检索链路**。

## 3. 节点拓扑

```
2.1 开始
  └→ clean_history（编码修复：latin-1 → utf-8）
      └→ 2.2 LLM-意图识别与字段提取
          └→ 2.3 代码-解析意图识别结果
              └→ 2.3A 代码-shownSessionIds清洗
                  └→ 2.4 条件-条件分支
                      ├─ CASE1 (course_enroll + ready=false) → 2.5 回复-补充信息
                      ├─ CASE2 (ready + offline_course + search_course)
                      │     → 2.15A 知识库-课程查询
                      │         └→ 2.15B 代码-解析课程知识库结果
                      │             └→ 2.15C 条件-课程知识库结果判断
                      │                 ├─ single / multiple → 2.15 HTTP-线下课查询-按课程标准化
                      │                 └─ none → 2.5 回复-补充信息
                      ├─ CASE3 (ready + offline_course + 非 search_course)
                      │     → 2.15D HTTP-线下课查询-按导师/城市
                      ├─ CASE4 (social_chat) → 2.18 LLM闲聊 → 闲聊回复
                      └─ ELSE → 兜底 / 去全部看看   ★ 要删
                  
2.15 / 2.15D → 2.16 解析查询结果 → 2.17 结果判断
    ├─ true (has_result + search_course) → 2.9 LLM线下课导语 → 2.13 统一回复
    ├─ has_result + 非 search_course      → 2.9B LLM通用导语 → 2.13 统一回复
    ├─ empty                              → 2.11 空结果提示
    └─ no_more                            → 2.12 没有更多
```

## 4. 关键发现

### 4.1 只有一个数据接口

两个 HTTP 节点打的是**同一个 URL**：

```
GET https://www.6qedu.cn/goods/api/product/periods/ai/list
```

| 节点 | 差异 |
|------|------|
| 2.15 按课程标准化 | `courseId` 来自知识库，`courseName` 留空 |
| 2.15D 按导师/城市 | `courseId` / `courseName` 硬编码为空字符串，只用 city / instructor / date |

请求体字段：`userId` `sessionId` `keyword` `courseId` `courseName` `city` `instructorName` `phaseNo` `dateFrom` `dateTo` `shownSessionIds`

> 注意：接口带 `userId` / `sessionId`，说明线上期数结果有用户维度逻辑（报读状态、推荐排序）。

### 4.2 意图只有 2 个值

`intent`：`course_enroll` | `other`
`course_category`：`offline_course` | `unknown`

Prompt 里写得很明确：「其余输出 other」。而 `other` 唯一出口就是「去全部看看」。

### 4.3 5 个 reply_mode 全都查期数

| reply_mode | 实际行为 |
|-----------|---------|
| `search_course` | 知识库归一化课名 → 按期数查 |
| `search_teacher` | **按导师名筛期数**，不是返回导师卡 |
| `search_city` | 按城市筛期数 |
| `follow_up` | 带 `shownSessionIds` 翻页 |
| `general_search` | 兜底，仍查期数 |
| `social_chat` | 闲聊，不检索 |

**这条很关键**：它回答了我之前问的「高EQ导师是什么」——现状没有导师实体，导师只是期数的一个筛选条件。v6 要做导师卡，等于新建一种业务实体，不是加个分支。

### 4.4 知识库是课程词典，不是内容库

- 数据集：1 个（ID 略）
- 检索：混合检索（向量 0.6 + 关键词 0.4），top_k=10，qwen3-rerank 重排
- query 变量：`course_name`
- 输出：`course_id` `course_name_full` `course_highlight_text`
- 三种命中态：`single`（唯一确认）/ `multiple`（多命中已选最优）/ `none`（未命中 → 补充信息）

**边界很干净**：知识库只放课名、课程 ID、亮点文案；期数/价格/名额走 HTTP。这条设计在 v6 要保留。

### 4.5 卡片与按钮的下行协议

APP 与 Dify 之间靠文本标记传结构化数据：

| 标记 | 用途 |
|------|------|
| `@s_obj@ ... @e_obj@` | 卡片数据，内容是 JSON 数组 |
| `@hsy ... @_hsy` | 隐藏元数据（课名、导师、城市、时间），不展示给用户 |
| `@s_obj@按钮:去全部看看@e_obj@` | 按钮 |

> **v6 必改**：8 类卡片共用 `@s_obj@` 时，JSON 里必须加 `type` 字段区分类目，否则 APP 无法渲染。现在只有一种卡片，没这个问题。

### 4.6 翻页与去重

- `shown_session_ids` 由 APP 传入，存在会话变量
- `2.3A` 节点只在 `reply_mode == follow_up` 时透传，其他模式清空
- 后端返回空 + 有 shownIds → `no_more` → 「没有更多的课程期数了」

### 4.7 现有兜底话术（v6 要删的）

```yaml
节点: 兜底 / 去全部看看
answer: |
  小Q暂不支持其他类型的智能检索哦
  你可以去全部看看：
  @s_obj@按钮:去全部看看@e_obj@
```

### 4.8 顺手发现的问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | `2.15` 请求体里 `"courseName":,` 是空值语法，JSON 不合法 | 若后端严格解析会报错，建议确认是否被容错 |
| 2 | 意图识别 temperature = 0.8 | 分类任务偏高，容易抖动；建议降到 0.1~0.3 |
| 3 | `2.13 统一回复` 同时引用 `2.9` 和 `2.9B` 两个 LLM 输出 | 靠分支互斥保证只有一个有值，属隐式依赖，改流程时易踩坑 |
| 4 | `clean_history` 做 latin-1→utf-8 逆修复 | 说明上游存在编码问题，是个补丁而非修复根因 |
| 5 | 节点标题编号混乱（2.9 / 2.9B / 2.15 / 2.15D / 2.11 / 2.12 / 2.13 交错） | 维护成本高，v6 建议重排编号 |

## 5. 对 v6 的直接含义

### 5.1 工作量重新评估

| 类目 | 现状 | v6 需要 |
|------|------|---------|
| 线下课程 | ✅ 完整链路（知识库+期数API+导语+翻页） | 基本复用 |
| 线上课程 | ❌ 无 | 意图+接口+卡片+导语 |
| 领袖营 | ❌ 无 | 意图+接口+卡片+导语 |
| 高EQ导师 | ❌ 无（目前只是筛期数的参数） | **新建实体**+接口+卡片 |
| 6Q商城 | ❌ 无 | 意图+接口+卡片+导语 |
| 文章 | ❌ 无 | 意图+接口+卡片+导语 |
| 视频 | ❌ 无 | 意图+接口+卡片+导语 |
| 音频 | ❌ 无 | 意图+接口+卡片+导语 |

**7 条新链路**，每条 = 意图分支 + HTTP 节点 + 解析代码 + 条件判断 + 空态 + 导语。

### 5.2 改造清单

**要删**
- `兜底 / 去全部看看` 节点及 ELSE 边
- Prompt 中 `intent` 只允许两值的约束
- Prompt 中「其余输出 other」的表述

**要改**
- `intent` → `intents`（数组）；或保持单值 + 新增 `sub_intents`
- `course_category` → 扩为 `data_category`，值域 8 类
- `@s_obj@` 卡片 JSON 增加 `type` 字段
- 意图 Prompt 从「课程会务判断」重写为「8 类分类」
- `2.4 条件分支` 从 4 个 CASE 扩到 8+N 个 CASE，或改为「按 category 路由到子工作流」

**要新增**
- 7 个检索 HTTP 节点（或 1 个聚合节点 `/search/multi`）
- 7 个结果解析代码节点
- 8 类卡片渲染协议约定
- 8 类导语生成（建议合并为 1 个 LLM 节点，按 category 分支出文案，避免 8 个 LLM 节点）

### 5.3 架构建议

现在 23 个节点撑 1 类数据。如果按同样方式堆 8 类，会变成 **150+ 节点**，无法维护。

建议改成**子工作流**结构：

```
主流程
  ├→ 意图识别（1 个 LLM，输出 intents[] + slots）
  ├→ 路由（按 intents 分发）
  │    ├→ 子流-线下课程
  │    ├→ 子流-线上课程
  │    ├→ 子流-领袖营
  │    ├→ 子流-导师
  │    ├→ 子流-商城
  │    ├→ 子流-文章
  │    ├→ 子流-视频
  │    └→ 子流-音频
  ├→ 并行聚合（多类并发）
  └→ 统一导语（1 个 LLM，读所有子流结果）
```

每个子流内部结构与现有「线下课程」一致（接口 → 解析 → 判断 → 空态），可复制。

## 6. 待你确认

1. **线上课程 / 领袖营 / 商城 / 文章 / 视频 / 音频的后端接口是否已存在？** 现有 DSL 只有期数一个接口，其余 7 类若无接口，Dify 改造完也跑不通。
2. **导师要不要做成实体卡？** 现状导师只是筛期数的参数。若要导师卡，需要导师列表接口 + 字段（头像、职称、擅长领域、在授课程数）。
3. **`intents` 是否允许一次命中多类？** 你已定 B（按意图命中），但需要确认多类并列的情况（如「恋爱咨询」命中文章+视频+音频）。
4. **是否同意改子工作流结构？** 否则节点数会失控。
